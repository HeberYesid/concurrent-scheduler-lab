# ADR-003: Patrón Pipeline para el Flujo de Simulación y Scheduling

## Estado
Aceptado

## Contexto
El flujo del scheduler consta de múltiples etapas secuenciales con diferentes responsabilidades y tipos de entrada y salida:
1. Lectura y Parseo: Recibir un stream de datos crudos (ej. formato CSV) y traducirlo a entidades de dominio.
2. Validación: Asegurar el cumplimiento de precondiciones y restricciones de dominio sobre los datos de entrada.
3. Planificación (Core): Simular la ejecución de los procesos aplicando colas de prioridad y envejecimiento, produciendo una corrida rica con métricas y trazabilidad de ejecución.
4. Recolección de Métricas: Procesar los tiempos de ejecución para derivar indicadores agregados (throughput, tiempo de espera promedio y tasa de starvation).
5. Formateo y Salida: Generar una representación visual o serializable de los resultados obtenidos.

Unificar estas etapas en un único bloque de código compromete la mantenibilidad, el testeo y la reutilización de componentes.

## Decisión
Se decide modelar este flujo aplicando el patrón **Pipeline**. Cada etapa se comportará como una función pura bien definida que toma una entrada tipo `T` y retorna una salida tipo `R`. 
Las transformaciones y encadenamientos se realizarán en base al tipo monádico `Result<T, E>` para asegurar el manejo limpio de errores sin interrumpir la secuencia con excepciones inesperadas, propagando el error de negocio de forma determinista.

El pipeline se compondrá de la siguiente manera:
```
[Entrada Cruda] -> (CsvProcessParser) -> Result<List<ProcessTask>, SchedulerError>
                -> (Validator)        -> Result<List<ProcessTask>, SchedulerError>
                -> (SchedulerService) -> Result<SchedulerRun, SchedulerError>
                -> (MetricsCollector) -> Result<SchedulerMetrics, SchedulerError>
                -> (ConsoleOutputFormatter) -> [Salida Consola]
```

## Alternativas Rechazadas
1. **Método Monolítico de Orquestación (God Class/Method)**:
   - *Desventaja*: Código altamente acoplado y difícil de mantener. Dificulta escribir pruebas unitarias específicas para componentes como el parseador CSV o el recolector de métricas.
2. **Chain of Responsibility**:
   - *Desventaja*: Este patrón está orientado a casos donde un request pasa por varios eslabones y cada uno decide si lo procesa o no de forma dinámica. En este sistema concurrente, la secuencia de ejecución es obligatoria y determinista para todas las fases, por lo que Chain of Responsibility añade complejidad de despacho innecesaria.

## Consecuencias
- **Ventajas**:
  - Desacoplamiento total: cada componente del pipeline tiene una única responsabilidad y puede ser probado en aislamiento de forma determinista.
  - La composición basada en `Result` hace el flujo resistente a fallos inesperados y documenta de forma explícita los errores esperados (ej. `EMPTY_PROCESS_LIST`, `DUPLICATE_PROCESS_ID`).
- **Desventajas**:
  - Requiere estructurar retornos encadenados con `flatMap`, lo que puede requerir familiaridad con programación funcional en Java.
