# ADR-003: Patrón Pipeline y Arquitectura Hexagonal para el Flujo del Scheduler

## Estado

Aceptado

## Contexto y Problemática

El flujo completo de una simulación del scheduler comprende cinco etapas secuenciales con responsabilidades y tipos de datos distintos:

| Etapa | Entrada | Salida | Responsable |
|---|---|---|---|
| 1. Parseo | CSV / texto crudo | `List<ProcessTask>` | `CsvProcessParser` |
| 2. Validación | `List<ProcessTask>` + `SchedulerConfig` | Datos validados o error | `SchedulerService` (fail-fast) |
| 3. Planificación | Procesos validados | `SchedulerRun` (traza + métricas) | `AgingSchedulerService` |
| 4. Recolección de métricas | `ExecutionRecord` × N | `SchedulerMetrics` | `StreamingMetrics` |
| 5. Formateo y salida | `SchedulerMetrics` | Texto formateado (consola) | `ConsoleOutputFormatter` |

Unificar estas etapas en un solo método monolítico compromete la mantenibilidad, la testeabilidad y la reutilización. Además, la guía académica exige Clean Architecture con separación estricta de responsabilidades.

## Motivación (Decision Drivers)

1. **Testeabilidad**: cada etapa debe ser verificable en aislamiento con dobles de prueba.
2. **Desacoplamiento**: cambios en el formato de salida (consola → JSON → HTML) no deben afectar la lógica de planificación.
3. **Manejo de errores**: los errores de dominio deben propagarse sin excepciones, usando un tipo monádico que fuerce al llamante a manejar el caso de error.
4. **Arquitectura hexagonal**: el dominio (`domain/`) no debe depender de la infraestructura (`infrastructure/`).
5. **Principio de responsabilidad única (SRP)**: cada clase debe tener exactamente una razón para cambiar.

## Opciones Consideradas

### Opción A: Método monolítico de orquestación (God Method)

- **Ventaja**: simple de escribir inicialmente.
- **Desventaja**: acoplamiento alto entre parseo, validación, simulación y formateo. Imposible testear componentes en aislamiento. Cada cambio en el formato de salida requiere modificar la lógica central.
- **Descartada** por violar Clean Architecture y SRP.

### Opción B: Chain of Responsibility

- **Ventaja**: cada eslabón decide si procesa o delega.
- **Desventaja**: el flujo del scheduler es determinista y secuencial — no hay decisión dinámica sobre qué etapa procesa qué. Chain of Responsibility añade complejidad de despacho innecesaria para un pipeline lineal.
- **Descartada** por complejidad injustificada.

### Opción C: Pipeline funcional con Result monádico

- **Ventaja**: cada etapa es una función pura con entrada/salida tipada. El encadenamiento con `Result<T, E>` (monádico) propaga errores sin excepciones. La arquitectura hexagonal separa dominio de infraestructura.
- **Desventaja**: requiere estructurar retornos con `flatMap`, que puede ser menos familiar en Java que en lenguajes funcionales puros. Sin embargo, Java 17 soporta pattern matching y expresiones lambda que facilitan este estilo.
- **Seleccionada** por máxima desacoplamiento, testeabilidad y alineación con Clean Architecture.

## Decisión

Se modela el flujo como un **Pipeline** compuesto por etapas independientes que se comunican mediante el tipo monádico `Result<T, E>`.

```
[Entrada CSV] → (CsvProcessParser) → List<ProcessTask>
              → (SchedulerService)  → Result<SchedulerRun, SchedulerError>
              → (MetricsCollector)  → SchedulerMetrics
              → (ConsoleOutputFormatter) → [Salida Consola]
```

### Regla de dependencia arquitectónica

```
domain/model       ← no depende de nadie (records puros)
domain/algorithm   ← depende solo de domain/model
domain/service     ← depende de domain/model y domain/algorithm
infrastructure/    ← depende de domain/service (interfaces) y domain/model
benchmark/         ← puede depender de todo (código de medición, no de producción)
```

Verificación: **cero imports de `com.proyecto.infrastructure` en `com.proyecto.domain`**.

### Manejo de errores con `Result<T, E>`

`Result` es un *sealed interface* con dos implementaciones: `Ok<T, E>` y `Err<T, E>`. Inspirado en `Result<T, E>` de Rust:

- `Result.ok(value)` → contiene el valor exitoso.
- `Result.err(error)` → contiene el error de dominio (`SchedulerError`).
- `map(Function<T, R>)` → transforma el valor si es `Ok`, propaga el error si es `Err`.
- `flatMap(Function<T, Result<R, E>>)` → encadena operaciones fallables.

Errores modelados:
- `EMPTY_PROCESS_LIST`: lista de entrada vacía.
- `INVALID_CONFIGURATION`: configuración nula.
- `DUPLICATE_PROCESS_ID`: IDs repetidos en la entrada.

El tipo `SchedulerError` es un `enum` con mensajes descriptivos. No se lanzan excepciones para flujo de control — los errores se retornan como valores.

## Consecuencias Positivas

- **Desacoplamiento total**: cada etapa del pipeline tiene una única responsabilidad y puede ser probada en aislamiento con valores predecibles. Cambiar el formato de salida (consola → JSON) no afecta la lógica de planificación.
- **Manejo explícito de errores**: el tipo `Result` fuerza al llamante a considerar el caso de error. No hay excepciones no declaradas que interrumpan el flujo.
- **Alineación con Clean Architecture**: `domain/` no conoce `infrastructure/`. Los puertos (`SchedulerService`, `ProcessRepository`, `MetricsCollector`) se definen en `domain/service/` y los adaptadores (`InMemoryProcessRepository`, `CsvProcessParser`, `ConsoleOutputFormatter`) en `infrastructure/`.
- **Testeabilidad mejorada**: cada componente del pipeline (parsers, validators, scheduler, metrics, formatter) tiene pruebas unitarias independientes. Las pruebas de integración (`SchedulerIntegrationTest`) verifican el pipeline completo end-to-end.

## Consecuencias Negativas, Riesgos y Mitigaciones

| Riesgo | Mitigación |
|---|---|
| `flatMap` encadenado puede ser menos legible que código imperativo | El pipeline principal está en `AgingSchedulerService.schedule()`, que usa un estilo procedural con early returns (`Result.err(...)`) para fail-fast. La monad se usa solo para componer resultados, no para lógica de negocio. |
| El patrón Pipeline definido en este ADR sugiere encadenamiento con `flatMap`, pero la implementación actual en `Main.java` usa un estilo más imperativo | ADR-003 define la **arquitectura conceptual** (separación de etapas, manejo de errores con `Result`). La implementación concreta en `Main` realiza el encadenamiento manualmente, lo cual es una decisión de estilo — el pipeline lógico se preserva. Las etapas pueden componerse con `flatMap` si se desea un estilo más funcional. |
| `ConsoleOutputFormatter` en `infrastructure/io/` está excluido de JaCoCo | La salida formateada es infraestructura de presentación (no lógica de negocio). Su contrato es devolver un `String` dado `SchedulerMetrics`, lo cual se verifica manualmente (inspección visual). |

## Confirmación

La decisión se valida mediante:
1. **Verificación de dependencias**: `grep -r "import com.proyecto.infrastructure" src/main/java/com/proyecto/domain/` retorna vacío — cero violaciones de la regla de dependencia.
2. **Pruebas de integración** (`SchedulerIntegrationTest`): 4 tests end-to-end que recorren el pipeline completo desde CSV hasta métricas.
3. **Pruebas del Result monad** (`ResultTest`): 3 tests que verifican `map`, `flatMap`, `isOk`/`isErr`, y rechazo de nulos.
4. **Pruebas de cada etapa en aislamiento**: `CsvProcessParser` (2 tests), `StreamingMetrics` (3 tests), `SchedulerService` (4 tests), `ConsoleOutputFormatter` (inspección manual).
