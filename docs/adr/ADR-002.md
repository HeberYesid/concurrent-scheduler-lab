# ADR-002: Patrón Strategy para el Cálculo de Prioridad Efectiva

## Estado

Aceptado

## Contexto y Problemática

La prioridad efectiva de un proceso en espera se define como:

$$\text{effectivePriority}(p, t) = (39 - p.\text{basePriority}) + f(\text{waitTime}, \alpha)$$

donde $f$ es una función de envejecimiento que pondera el tiempo de espera acumulado con un factor $\alpha \in (0, 1]$.

Diferentes tipos de cargas de trabajo o escenarios de simulación demandan distintas curvas de envejecimiento:

- **Lineal**: crecimiento constante, adecuado para cargas balanceadas.
- **Exponencial/Logarítmica**: crecimiento atenuado para ráfagas largas, evita que procesos longevos monopolicen la CPU.
- **Escalonada (Step)**: incrementos discretos por intervalos, modela sistemas de tickets o quantums.

Se requiere poder intercambiar la fórmula de envejecimiento en tiempo de configuración sin modificar el motor de aging ni el scheduler principal.

## Motivación (Decision Drivers)

1. **Extensibilidad**: nuevas fórmulas de aging deben agregarse sin modificar código existente (Open/Closed Principle).
2. **Testeabilidad**: cada fórmula debe poder verificarse en aislamiento con valores predecibles.
3. **Desacoplamiento**: el `AgingEngine` y el `AgingSchedulerService` no deben contener lógica condicional dependiente de la estrategia de aging elegida.
4. **Simplicidad**: la interfaz debe ser mínima (una sola operación).

## Opciones Consideradas

### Opción A: Fórmulas Hardcoded con `if/else` o `switch`

- **Ventaja**: sin indirección, cero overhead de despacho.
- **Desventaja**: viola el Open/Closed Principle. Cada nueva fórmula requiere modificar `AgingEngine` o `AgingSchedulerService`, con riesgo de regresiones. No permite agregar estrategias en tiempo de ejecución sin recompilar.
- **Descartada** por fragilidad ante cambios y acoplamiento alto.

### Opción B: Enum con `switch` interno

- **Ventaja**: centraliza las fórmulas en una sola clase.
- **Desventaja**: la clase crece con cada nueva estrategia. No permite extensión por terceros sin modificar el enum. La lógica condicional (`switch`) tiene mayor complejidad ciclomática.
- **Descartada** por limitar la extensibilidad abierta.

### Opción C: Patrón Strategy con interfaz funcional

- **Ventaja**: cada estrategia es una clase independiente que implementa `PriorityCalculator`. Agregar una estrategia es crear una nueva clase, sin tocar código existente. La interfaz `@FunctionalInterface` permite usar lambdas para testing rápido.
- **Desventaja**: una indirección adicional por despacho virtual (costo ~2 ns en JIT, insignificante comparado con el costo real de `Math.log` o aritmética de aging).
- **Seleccionada** por maximizar extensibilidad, testeabilidad y desacoplamiento.

## Decisión

Se implementa el patrón **Strategy** mediante la interfaz funcional `PriorityCalculator`:

```java
@FunctionalInterface
public interface PriorityCalculator {
    double calculate(ProcessTask process, long currentTime, SchedulerConfig config);
}
```

Se proveen tres implementaciones concretas en `com.proyecto.domain.algorithm`:

1. **`LinearAgingCalculator`**: crecimiento lineal.
   $$\text{prioridad} = (39 - \text{basePriority}) + \alpha \times \text{waitTime}$$

2. **`ExponentialAgingCalculator`**: crecimiento logarítmico (atenúa ráfagas largas).
   $$\text{prioridad} = (39 - \text{basePriority}) + \alpha \times \log_2(1 + \text{waitTime})$$

3. **`StepAgingCalculator`**: incrementos discretos cada `agingInterval`.
   $$\text{prioridad} = (39 - \text{basePriority}) + \alpha \times \left\lfloor \frac{\text{waitTime}}{\text{agingInterval}} \right\rfloor$$

El `AgingEngine` recibe la estrategia por inyección de dependencia en su constructor y delega el cálculo a `calculator.calculate(process, currentTime, config)`.

## Consecuencias Positivas

- **Extensibilidad máxima**: agregar una nueva fórmula de aging requiere únicamente crear una clase que implemente `PriorityCalculator`. Cero modificaciones a `AgingEngine` o `AgingSchedulerService`.
- **Desacoplamiento total**: `AgingEngine` depende solo de la abstracción `PriorityCalculator`, no de implementaciones concretas.
- **Testeabilidad en aislamiento**: cada calculadora se verifica con tablas de valores predecibles (ej. waitTime=0 devuelve `39 - basePriority`, crecimiento proporcional verificado con aserciones exactas).
- **Configurabilidad**: `Main` instancia la estrategia deseada (`LinearAgingCalculator`, `ExponentialAgingCalculator`, `StepAgingCalculator`) y la inyecta en el scheduler.

## Consecuencias Negativas, Riesgos y Mitigaciones

| Riesgo | Mitigación |
|---|---|
| Indirección por despacho virtual (~2 ns/llamada) | La JVM aplica *inline caching* y JIT *devirtualization* para llamadas monomórficas. El costo es insignificante comparado con las operaciones aritméticas y logarítmicas de las fórmulas de aging. |
| `ExponentialAgingCalculator` contiene estado (`LN_2`) a pesar de que la interfaz es `@FunctionalInterface` | La constante `LN_2` es `static final` — no es estado de instancia. La clase sigue siendo funcionalmente pura. |
| Las tres fórmulas comparten la constante `39` (duplicada en cada clase) | Mitigado: todas referencian `ProcessTask.MAX_PRIORITY`, eliminando la duplicación literal. Si el rango de prioridades cambiara, todas las calculadoras se adaptan automáticamente. |
| Precisión de punto flotante | `waitTime` y `agingFactor` son `long` y `double`. El error relativo de IEEE 754 es $< 10^{-15}$, irrelevante para comparaciones de prioridad. Los desempates por `arrivalTime` e `id` garantizan orden total determinista aun ante empates por redondeo. |

## Confirmación

La decisión se valida mediante:
1. **Pruebas unitarias** (`AgingStrategiesTest`): 5 tests con valores exactos para las 3 calculadoras, incluyendo validaciones de contrato (null, currentTime < arrivalTime).
2. **Pruebas de integración** (`SchedulerIntegrationTest`): verificación de orden de ejecución correcto con aging lineal.
3. **Benchmarks JMH**: `fullCycle` mide las 3 estrategias en `Main` para 20K procesos mixtos.
4. **PIT mutation testing**: las 3 calculadoras tienen 100% de cobertura de mutaciones (cero sobrevivientes en `MathMutator` y `ConditionalsBoundaryMutator` para estas clases).
