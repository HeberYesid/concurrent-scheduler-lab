# ADR-001: Estructura de Datos para la Cola de Prioridad del Scheduler

## Estado

Aceptado

## Contexto y Problemática

El scheduler de procesos debe seleccionar el siguiente proceso a ejecutar en $O(\log n)$ y soportar inserciones eficientes para escalas de $N = 1\,000$ a $N = 500\,000$ procesos simultáneos.

La operación diferencial del problema es el **envejecimiento (aging)**: periódicamente, todos los procesos en espera recalculan su prioridad efectiva en función del tiempo acumulado. Esta actualización masiva de claves de ordenación debe realizarse sin degradar la latencia de selección.

Restricciones:
- El sistema opera en memoria (sin persistencia externa durante la simulación).
- La memoria disponible por proceso debe ser baja para alcanzar $N = 500\,000$ (~32 MB total para el heap).
- La implementación debe ser mantenible y verificable por un equipo académico.

## Motivación (Decision Drivers)

1. **Costo de aging**: la operación de actualización masiva de prioridades es inevitable para garantizar anti-starvation. Su complejidad domina la elección de estructura.
2. **Latencia de selección**: cada extracción del siguiente proceso debe ser $O(\log n)$ en peor caso.
3. **Localidad de caché**: en simulaciones con miles de procesos, los cache misses pueden multiplicar por 3-5x el factor constante.
4. **Simplicidad de implementación**: una estructura compleja aumenta el riesgo de bugs en un contexto académico con tiempo limitado.
5. **Determinismo**: el comportamiento debe ser reproducible para testing y depuración.

## Opciones Consideradas

| Criterio | Binary Max-Heap (array) | Árbol Rojo-Negro | Skip List | Lista Ordenada |
|---|---|---|---|---|
| Insert | $O(\log n)$ | $O(\log n)$ | $O(\log n)$* | $O(n)$ |
| ExtractMax | $O(\log n)$ | $O(\log n)$ | $O(1)$ | $O(1)$ |
| **Aging (update all)** | $\mathbf{O(n)}$ | $O(n \log n)$ | $O(n \log n)$ | $O(n \log n)$ |
| Espacio/elem | ~64 B | ~120 B | ~80 B* | ~64 B |
| Cache locality | Excelente | Pobre | Media | Buena |
| Implementación | Simple (~100 LOC) | Media | Compleja (~200 LOC) | Trivial |

*\* Skip List: caso esperado; peor caso $O(n)$ para espacio.*

### Árbol Rojo-Negro (TreeSet / TreeMap de Java)
- El aging requiere remover y reinsertar cada nodo para actualizar su clave de ordenación.
- Costo de aging: $O(n \log n)$. Para $N = 500\,000$, ~9.5 millones de operaciones por ciclo.
- Overhead de memoria: cada nodo requiere referencias a hijo izquierdo, hijo derecho, padre y color (+87% respecto al heap).
- Descartado por costo de aging prohibitivo y baja localidad de caché.

### Skip List
- ExtractMax en $O(1)$ es atractivo, pero el aging sigue requiriendo $O(n \log n)$ para reubicar todos los nodos tras el cambio de prioridad.
- Factor constante mayor debido a asignación aleatoria de niveles y punteros dispersos.
- Espacio no determinístico: $O(n \log n)$ en peor caso.
- Descartado por complejidad de implementación injustificada para un problema sin range queries.

### Lista Ordenada
- Inserción $O(n)$ — completamente inaceptable para $N \ge 10\,000$.
- Descartada sin discusión adicional.

### Fibonacci Heap (no incluida en tabla)
- `decreaseKey` $O(1)$ amortizado teórico, pero constant factors enormes en práctica.
- Implementación ~500 líneas, extremadamente compleja de verificar.
- Peor cache behavior que binary heap (nodos enlazados).
- Benchmarks reales muestran que binary heap es más rápido para $N < 10M$.

## Decisión

Se implementa un **Binary Max-Heap sobre arreglo contiguo redimensionable**, con reconstrucción periódica mediante el **algoritmo de Floyd** (*bottom-up heapify*) para la operación de aging.

Mecanismo de aging:
1. Las prioridades efectivas se mutan *in-place* sobre cada elemento del arreglo.
2. Se reconstruye la propiedad de heap en $O(n)$ mediante Floyd: `for i = n/2-1 down to 0: siftDown(i)`.
3. El intervalo de aging se configura mediante `agingInterval` (típicamente 100 ms).

## Consecuencias Positivas

- **Insert y extractMax en $O(\log n)$ peor caso garantizado**: el heap binario es determinístico y analizable formalmente.
- **Aging en $O(n)$**: 19× más rápido que la mejor alternativa basada en árboles para $N = 500\,000$.
- **Excelente localidad de caché**: el arreglo contiguo reduce cache misses, manteniendo el factor constante ~3-5× menor que estructuras basadas en punteros.
- **Bajo overhead de memoria**: ~64 bytes por proceso, permitiendo simular 500K procesos en ~32 MB de heap.
- **Implementación simple**: ~100 líneas de código facilitan la verificación, el testing y la defensa académica.

## Consecuencias Negativas, Riesgos y Mitigaciones

| Riesgo | Mitigación |
|---|---|
| El aging rebuild $O(n)$ puede bloquear el scheduler si `agingInterval` es muy pequeño, degradando el costo total a $O(n^2)$ para $N$ grande. | Calibrar `agingInterval \ge 10 \times B_{avg}$ donde $B_{avg}$ es el burstTime promedio. Con $B_{avg} \approx 50$ ms, `agingInterval = 100` ms es seguro. El análisis amortizado (§5.1 del informe técnico) demuestra que el costo por proceso tiende a $O(1)$ cuando `agingInterval` es grande relativo a $B_{avg}$. |
| No soporta `decreaseKey` / `increaseKey` eficiente sobre elementos individuales. | No requerido por el problema actual. Si se necesitara cancelar procesos individuales en el futuro, migrar a *Indexed Heap* (heap con tabla hash de posiciones). |
| La mutación in-place de prioridades rompe temporalmente la propiedad de heap hasta que se ejecuta el rebuild. | El rebuild se ejecuta inmediatamente después de la mutación, sin intercalar operaciones de extracción. El invariante se restaura en una sola pasada $O(n)$. |
| El arreglo interno usa `Object[]` con casts unchecked (sin tipo genérico en tiempo de ejecución). | Los casts son seguros porque el heap solo acepta elementos del tipo parametrizado `<T>`. Se suprime la advertencia con `@SuppressWarnings("unchecked")`. |

## Confirmación

La decisión se valida mediante:
1. **Pruebas de propiedad con jqwik**: 3 propiedades que verifican el invariante de heap y la extracción en orden descendente sobre 1000 listas aleatorias cada una.
2. **Benchmarks JMH**: medición empírica de `insertAndExtract` y `agingRebuild` para $N = \{1K, 10K, 100K, 500K\}$.
3. **PIT mutation testing**: 86% de cobertura de mutaciones sobre el código del heap.
4. **Análisis de complejidad formal**: §5 del informe técnico.
