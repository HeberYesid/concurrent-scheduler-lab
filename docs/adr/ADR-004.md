# ADR-004: Patrón Command para Trazabilidad, Auditoría y Rollback del Heap

## Estado

Aceptado

## Contexto y Problemática

El simulador del scheduler realiza tres tipos de operaciones mutables sobre la cola de prioridad `MaxHeap`:

1. **Inserción** de nuevos procesos que llegan al sistema.
2. **Extracción** del proceso con mayor prioridad efectiva para su ejecución.
3. **Envejecimiento masivo (aging)**: recálculo de todas las prioridades efectivas más reconstrucción del heap.

Para propósitos de depuración, verificación de corrección en pruebas unitarias y auditoría de la secuencia de scheduling, se necesita:

- Un historial auditado de cada operación ejecutada.
- Capacidad de **deshacer (undo)** operaciones para restaurar el estado previo del heap sin corromper su consistencia interna.
- Que las pruebas puedan ejecutar una secuencia de operaciones, verificar estados intermedios, y revertir para confirmar que el estado se restaura correctamente.

El heap es una estructura mutable. Si una operación falla a mitad de ejecución durante una simulación, restaurar el heap a su estado previo sin un mecanismo de rollback requeriría reiniciar la simulación completa.

## Motivación (Decision Drivers)

1. **Testeabilidad**: las pruebas unitarias deben poder ejecutar, verificar y deshacer operaciones sobre el heap sin reiniciar el contexto de prueba.
2. **Auditoría**: cada mutación del heap debe ser trazable para depurar errores de ordenamiento o aging.
3. **Rollback**: ante una falla lógica (no de sistema), debe ser posible revertir la última operación sin perder el estado anterior.
4. **Separación de responsabilidades**: la lógica de ejecución, historial y reversión no debe mezclarse con la lógica del heap.
5. **Costo de memoria controlado**: los snapshots para rollback no deben causar OOM en simulaciones con $N = 500\,000$.

## Opciones Consideradas

### Opción A: Logging simple (bitácoras de texto)

- **Ventaja**: implementación trivial con `System.out.println` o `java.util.logging`.
- **Desventaja**: informa sobre lo ocurrido pero no permite reconstruir programáticamente el estado anterior del heap para aserciones automáticas en pruebas. El rollback sería manual.
- **Descartada** por no satisfacer el requisito de testeo programático.

### Opción B: Event Sourcing completo

- **Ventaja**: registro inmutable y completo de todos los eventos, permitiendo reconstruir cualquier estado pasado. Persistencia opcional.
- **Desventaja**: excesivamente complejo para un simulador académico en memoria. Implica diseño de eventos, snapshots, proyecciones y posiblemente frameworks externos (Axon, EventStore). El overhead de desarrollo no se justifica para el alcance del proyecto.
- **Descartada** por complejidad desproporcionada.

### Opción C: Patrón Command con snapshots de estado

- **Ventaja**: cada operación se encapsula en un objeto `Command` con métodos `execute()` y `undo()`. El `undo()` restaura el estado desde un snapshot tomado antes de la ejecución. El historial se gestiona mediante una pila LIFO (`CommandHistory`).
- **Desventaja**: los snapshots consumen memoria ($O(n)$ por comando de aging). Para $N = 500\,000$, un snapshot del heap ocupa ~32 MB adicionales.
- **Seleccionada** por balance óptimo entre funcionalidad y complejidad.

## Decisión

Se implementa el patrón **Command** con las siguientes interfaces y clases:

```java
public interface SchedulerCommand {
    void execute();
    void undo();
}
```

### Comandos concretos

| Comando | `execute()` | `undo()` |
|---|---|---|
| `InsertProcessCommand` | Toma snapshot del heap, inserta el proceso. | Restaura el heap desde el snapshot. |
| `ExtractMaxCommand` | Toma snapshot, extrae el máximo y lo almacena. Expone `getExtracted()` para inspección. | Restaura el heap desde el snapshot. |
| `ApplyAgingCommand` | Toma snapshot del heap + snapshot de todas las prioridades efectivas, aplica aging via `AgingEngine`. | Restaura cada prioridad individual desde el snapshot de prioridades, luego restaura el orden del heap desde el snapshot estructural. |

### Gestor de historial

`CommandHistory` mantiene una pila `Deque<SchedulerCommand>` (LIFO) con operaciones:

- `executeAndRecord(cmd)`: ejecuta y apila.
- `undoLast()`: desapila y deshace.
- `clear()`: vacía el historial.
- `size()`: consulta la cantidad de comandos acumulados.

### Gestión de memoria

Para simulaciones de producción y benchmarks JMH ($N = 500\,000$), el historial de comandos **no se utiliza** — las operaciones se ejecutan directamente sobre el heap sin registrar snapshots. El patrón Command se activa exclusivamente durante pruebas unitarias y depuración. Esto mantiene la huella de memoria de producción en $O(1)$ adicional (sin historial) mientras que las pruebas gozan de rollback completo.

## Consecuencias Positivas

- **Pruebas unitarias avanzadas**: `CommandPatternTest` (10 tests) valida execute/undo para inserción, extracción y aging, incluyendo casos borde (undo sobre heap vacío, undo sin execute previo, validaciones de nulidad).
- **Trazabilidad**: cada comando encapsula el estado previo, permitiendo inspeccionar qué cambió exactamente en cada operación.
- **Rollback determinista**: el `undo()` restaura exactamente el estado anterior, sin depender de heurísticas de reverse-engineering del heap.
- **Separación limpia**: la lógica de historial y rollback está completamente fuera del `MaxHeap`. El heap solo expone `getState()` y `restoreState()` como primitivas de serialización/deserialización de su estado interno.

## Consecuencias Negativas, Riesgos y Mitigaciones

| Riesgo | Mitigación |
|---|---|
| Snapshots del heap para $N = 500\,000$ ocupan ~32 MB adicionales por comando de aging. | El historial de comandos **no se activa en producción**. Se usa solo en pruebas unitarias (escalas pequeñas, típicamente $N < 150$). En benchmarks JMH, las operaciones se ejecutan directamente sin pasar por `CommandHistory`. |
| `ApplyAgingCommand` requiere doble snapshot (estructura del heap + prioridades). | La memoria total para $N = 150$ (tamaño típico de pruebas) es insignificante (~10 KB). Para escalas mayores, el patrón no se utiliza. |
| `restoreState()` crea un nuevo arreglo para el heap, lo cual es $O(n)$. | Solo se llama durante `undo()` en pruebas, nunca en el flujo de producción. |
| `MaxHeap.getState()` y `restoreState()` exponen el arreglo interno (leaky abstraction). | Son métodos `public` pero documentados como "para uso de Command y pruebas". Alternativas como Memento pattern añadirían complejidad sin beneficio para el alcance actual. |

## Confirmación

La decisión se valida mediante:
1. **`CommandPatternTest`** (10 tests): inserción con undo, extracción con undo y verificación de `getExtracted()`, aging con undo y verificación de restauración de prioridades, undo sobre historial vacío, clear, validaciones de nulidad en todos los comandos.
2. **`MaxHeapUnitTest`**: 3 tests dedicados a `getState()` y `restoreState()`, verificando independencia mutua (modificar el arreglo retornado no afecta al heap) y restauración correcta tras extracción.
3. **PIT mutation testing**: `ApplyAgingCommand`, `InsertProcessCommand`, `ExtractMaxCommand` y `CommandHistory` tienen 90%+ de cobertura de mutaciones.
